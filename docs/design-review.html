earworm design review

earworm already does the hard part of TUI design: it says what mode it is in, hides keys that cannot work, and never blocks the screen on a subprocess. What is left is the layer that separates a tool you tolerate from one you reach for. This is a full pass, small things included, with a tasklist at the end.

What to keep

A review that is all defects misleads. These are the decisions I would defend against anyone who wanted to "modernise" them.

  • Mode bands that cover the gradient. You cannot be in a filtered or picking list without knowing.
  • Keys that vanish when they cannot work, and a status bar that says why (♪ cliamp off).
  • Two threads, one channel each way. Nothing on screen ever waits for yt-dlp.
  • The was … column. A wrong identification is visible without opening the file.
  • Filenames that never encode a guess. Only ok and manual tracks get renamed.
  • Esc unwinds one layer at a time and no longer ends the session.
  • Colour as confidence, word as provenance. Teal is checked, sand is a guess, red is broken.
  • One name column per list, so the dim detail columns line up.

The lens

The TUIs people keep, lazygit, fzf, k9s, helix, share a handful of habits. Every screen names its keys somewhere the eye already rests. Rare actions live behind one key rather than many. Nothing destructive is one keystroke from a mistake. The layout has tiers, so a narrow terminal degrades on purpose rather than by accident. And the copy sounds like one person who knows the tool, in the same register from the first prompt to the exit summary. Each finding below is one of those habits, applied to a specific spot in earworm.

AStarting out

  1. A1
    A missing binary should say how to get it. "yt-dlp not found on PATH" is correct and unhelpful. The requirements table in the README already knows the Homebrew formula; the error should carry it: yt-dlp not found · brew install yt-dlp.
  2. A2
    An earworm --check that reports the whole setup. yt-dlp, ffmpeg, fpcalc, cliamp, the AcoustID key, the config file it found and the format it resolved, one row each with a tick or the fix. This is the first thing a new user runs and the first thing you ask for in a bug report.
  3. A3
    Guard the minimum size. Below about 40 columns the header truncates into fragments and the band loses its hint. One dim centred line, needs 40 columns, is honest; fragments look like a crash.
  4. A4
    The intro needs an off switch. Two seconds is right the first twenty times. An intro = false config key costs nothing and is where a daily user will look. Keep the default on.
  5. A5
    Respect the terminal's colour depth. Every colour is RGB. On a 256-colour terminal (default macOS Terminal.app without truecolor, many SSH sessions) the gradient becomes bands and the cream can fall to grey. Detect COLORTERM=truecolor; otherwise quantise to the nearest 256-colour index once, at startup. Honour NO_COLOR with a flat palette.
  6. A6
    The first-run URL prompt is a good moment to teach one thing. Its note is empty. One dim line, "a playlist or a single video · Esc quits", tells a newcomer both facts they need before typing anything.

BWatching a run

  1. B1
    The header's right half is empty on every screen. That is prime real estate. During a run it should carry overall progress: ▰▰▰▰▱▱▱▱ 12/40 · 3m left. yt-dlp reports per-track percent already; settled-over-total plus a running average per track gives an estimate that is good enough and improves as it goes.
  1. B2
    Quitting mid-download deserves one question. Esc is now safe, but q still kills yt-dlp instantly. A two-option prompt, "12 of 40 downloaded · keep going / quit", only while done.is_none(), and ^c stays instant for the person who means it.
  2. B3
    Keep the cursor off the last row. Vim calls it scrolloff. When the cursor moves it should stay two rows clear of the pane's edge so the next row is visible before you reach it. ratatui's ListState supports an offset; three lines in draw_tracks.
  3. B4
    Set the terminal title. One OSC 2 write per stage: earworm · Focus · 12/40. It is what you see in the tab strip while doing something else, and it costs a print!.
  4. B5
    Say when a long run finishes. A BEL, or OSC 9 on terminals that show notifications, when the run settles and the window is not focused. Config key notify, default on. A forty-minute sync is exactly when the user has gone to do something else.
  5. B6
    The log pane should scroll. It shows the tail only. With l open, j/k could move the log instead of the list, or L could grow it to half the body. The line you need is the ERROR forty lines up.
  6. B7
    Follow mode should announce itself. f toggles silently. A dim following in the status bar while it is on, and a flash when a movement key switches it off, so the cursor jumping to the active track never looks like a bug.

CChoosing tracks

  1. C1
    The band could say what is selected, not only how many. PICK 158 of 361 selected is right. Adding the total duration where durations are known, · 9h 12m, turns the number into a decision about disk and time.
  2. C2
    Enter with nothing marked equals Esc. Both download nothing. That is consistent but surprising when someone unmarks everything by accident with a. A flash, nothing selected · a marks all · esc downloads none, and stay in the pick.
  3. C3
    Invert selection. a toggles everything the filter shows. A (or i) inverting the marks makes "everything except these three" one keystroke.

DFixing tags

This is what earworm is for, and it is where the largest gains are. Everything here is about reducing the number of prompts a person walks through to correct one track.

  1. D1
    Edit artist and title in one form. Today e asks two questions in sequence. A two-field popup with Tab between fields, the original video title shown dim beneath as reference, and ^s to swap the two fields in place. One prompt, one Enter.
  1. D2
    A detail pane for the selected track on wide terminals. The library has one at 100 columns; the track list should too. Full title, artist, album, source, note, duration, the file path, and the original video title untruncated. The row truncates was at 32 characters, and the truncated part is often the part that tells you what went wrong.
  2. D3
    Undo the last tag change. One level, u, holding the previous artist and title for the last track written. Tag edits are the only thing earworm does that is both easy to get wrong and immediate. Bulk s and A would undo as a set.
  3. D4
    Number the choices. Every Prompt::Choice is j/k/Enter. Digits 1 to 9 choosing directly, and y/n for two-option prompts, halve the keystrokes on the artist-conflict question that fires most.
  4. D5
    Show the cover before choosing it. The cover prompt lists sources by name. Terminals that support Kitty or Sixel graphics could preview; the rest get dimensions and byte size next to each option, which is enough to reject a 120px thumbnail.
  5. D6
    Mark by artist, not only by status. m marks every track sharing the cursor's status. The other question people have is "every track by this artist". M for that; the filter can do it today but needs typing.
  6. D7
    Jump between tracks that need attention. n and N to the next and previous unverified or failed row. Filtering hides context; jumping keeps it.

EThe library

  1. E1
    The library needs / too. Twenty playlists is a page; sixty is a search. The filter code is generic enough to run over shelf names.
  2. E2
    Sort order should be a choice. Alphabetical is the only order. o cycling name → last synced → most missing puts the folder that needs a sync at the top.
  3. E3
    Title the preview pane. It has a left border and nothing else, so it floats. A dim first line, 42 tracks · 2 missing, anchors it and repeats the one number that matters when the list truncates.
  4. E4
    A footer total. The header says 7 playlists. The status bar could say 412 tracks · 3 missing · last sync 2h ago: the whole library's health in one line.
  5. E5
    Open the folder outside earworm. o to reveal in Finder (open) or the platform equivalent. Everything downstream of earworm happens in a file manager or a player, and today you retype the path.

FFinishing

  1. F1
    The finish menu should lead with what needs a decision. Its note is the summary; its rows are keep, play, another, quit. When tracks are unverified, the first row should be review 9 guesses, which closes the menu with the filter set to the unverified statuses and the cursor on the first. That is the action the run is asking for.
  2. F2
    The exit summary should include the folder as a path you can use. It does say 12 tracks in ~/Music/Focus. Printing the folder on its own final line, unquoted, means cd "$(earworm … | tail -1)" works and a double-click selects it.
  3. F3
    Format belongs on this menu. "Next time as flac" is a thought you have at the end of a run, on a screen where f means follow. One row, present when the config file is writable.

GVoice and messages

  1. G1
    Flash duration should scale with length. Four seconds fits saved track 12 and not cliamp: playlist import failed: invalid playlist name …. 2s plus 50ms a character, capped at 8s, and a flash that arrives while another is showing should queue rather than replace.
  2. G2
    Align the stage words with the status words. The header says identifying while rows say reading; reading playlist is the scan but reading on a row is tag reading. Pick one verb per activity and use it in both places.
  3. G3
    Write down the voice. The copy is already good: lower case, short, active, a middle dot between clauses. Six lines in CLAUDE.md saying so keeps the next feature from introducing "Successfully saved!". Include the rule that a message names the thing it is about (saved track 12, never saved).
  4. G4
    Errors should end with the fix. failed: the edited config no longer parses is true. … no longer parses · check the format line in ~/.config/earworm/config.toml is useful. Every bail! that a user can hit should carry a next step.

HThe command line

Half of a CLI's experience happens before the TUI opens. This part is under-invested relative to the screens.

  1. H1
    --list --json. The table is for people; a JSON array of shelves (name, path, url, tracks, missing, synced) is for the shell script that wants to sync the stale ones. Ten lines with serde.
  2. H2
    Shell completions. clap_complete generates them; earworm --completions zsh prints them. Homebrew users expect tab-completion of flags and they notice its absence.
  3. H3
    Group the help. --help is one flat list of fourteen flags. clap's help_heading groups them: what to download, what to do to it, where the config comes from, actions that exit. The --no-* negation rule deserves one sentence in after_help.
  4. H4
    Refuse a non-TTY politely. Piped or in CI, crossterm's raw mode fails with an OS error. Detect it and say earworm needs a terminal · --list and --check work without one.
  5. H5
    Document exit codes. They exist and are correct. A line in the README and in --help, 0 finished · 1 failed · 2 bad arguments, is what makes them usable.
  6. H6
    --show-config. Print the effective configuration after merging file, flags and environment, with the source of each value. It answers "why is lookup off" without a bug report.

ITerminals and access

  1. I1
    Mouse: click to select, wheel to scroll. crossterm's EnableMouseCapture plus two match arms. Keyboard stays primary; the wheel is what people reach for on a 300-track list without thinking.
  2. I2
    A motion = false config key. Turns off the intro and the spinner, leaves everything else. Vestibular sensitivity is real and a braille spinner at 8 Hz is exactly the kind of thing that triggers it.
  3. I3
    Every state has a glyph as well as a colour. Mostly true already: statuses are words, missing files carry !. The playing marker and the follow state are colour-only or absent; give both a glyph.
  4. I4
    Test at 80×24 and 200×50 in CI. The buffer tests exist and are good. Two fixed-size renders of every screen, asserted against a snapshot, catch the "who moved the sync column" class of regression before a human does.

If you do three things

Confirm q during a download (B2), because it is the last way to lose work with one key. Put the edit into one form (D1), because fixing tags is the job and it currently takes twice the prompts it needs. Use the header's right half (B1), because a run you can watch is a run you trust. Everything else is worth doing; those three change how the tool feels.
